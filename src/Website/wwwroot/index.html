Hotelly

Searching, filtering, sorting, and paging data owned by different services.

How it works

  1. Each service owns its data. Registry owns the hotels, Sales the nightly rates, Reservations the availability, and Marketing the reviews. Each one has its own database.
  2. Search data meets in one place. Each service replicates only the columns search needs to its own schema in the search database, using PostgreSQL logical replication. No service can write to another one's schema.
  3. The search runs in the gateway. When you change a filter, this page calls the composition gateway: GET /search. The search process starts from Registry's hotels, and each service's providers add their part to the same query: filters narrow it, facets count the filtered hotels, sorts order them. The search database runs it, and only a page of hotel IDs comes back.
  4. Services compose the results page. The gateway raises a HotelsFound event with the page of IDs. Registry, Sales, and Marketing each load what they own for the whole page, with one query to their own database, and add it to the results.
  5. Look under the hood. The request and the composed response are at the bottom of the results. The colors tell you which service owns each filter and each piece of data: hover the i icons for details.

Stay i Two services use the dates. Reservations removes hotels with a sold-out night in the stay. Sales removes hotels it can't price for every night, then prices the stay: the sum of the nightly rates, which change with the season. Without dates, prices are "from" prices: the lowest nightly rate in the next 30 days.
City i Registry owns this filter and its facet. Counts are how many hotels match all the current filters, this one included.
Stars i Registry: hotels with any of the selected stars. The counts come from Registry's facet, built over the filtered hotels, including the stars filter itself: that's why the other values drop to 0 once you select one. Real sites build each facet without its own filter. The demo doesn't: filters don't declare which parameter they handle, so the search process can't leave one out.
Amenities i Registry: hotels with all the selected amenities. Each count is how many of the current results have that amenity.
Guest rating i Marketing owns this filter and facet: the average rating of each hotel's reviews, from 1 to 5. The bands overlap: a hotel rated 4.5 counts in all of them. Hotels without reviews never match.

Searching…

i Each sort key belongs to a service: stars to Registry, price to Sales, rating to Marketing. In the order you pick, the search process asks each one to add an OrderBy or a ThenBy to the same query, so sorting by price, then by rating, runs in the database. Hotels without a value, like no reviews or no price, come last in both directions. The hotel ID breaks ties, so pages never overlap.
